The clean version is to have Lumen tell Prometheus what to scrape, since Lumen already knows every backend.
http_sd against Lumen
 
yaml
Plain Text
  - job_name: backendshttp_sd_configs:- url: http://lumen:8000/metrics/targetsrefresh_interval: 60sbasic_auth:username: metricspassword: yourpasswordmetrics_path: /metrics
The endpoint returns a JSON array, Content-Type: application/json:
 
json
Plain Text
[{"targets": ["spark0:8000"],"labels": {"lumen_model": "ornith-1.0-35b", "engine": "vllm", "host": "spark0"}},{"targets": ["h200-1:30000"],"labels": {"lumen_model": "glm-5.2", "engine": "sglang", "host": "h200-1"}}]
Prometheus re-polls every 60s and picks up new targets with no reload and no restart. Add a model to Lumen's config, it shows up in monitoring on the next poll.
Roughly, in the metrics blueprint:
 
python
Plain Text
@bp.route("/targets")@requires_metrics_authdef sd_targets():    out = []for name, m in iter_models():           # however Lumen holds theseif m.get("engine") not in ("vllm", "sglang"):continue                        # skip OpenAI/Anthropic passthrough        u = urlparse(m["base_url"])        out.append({"targets": [u.netloc],"labels": {"lumen_model": name,"engine": m["engine"],"host": u.hostname},})return jsonify(out)
Two things to get right. Filter out hosted providers, since they have no /metrics and would show as permanently down targets. And do not name the label model_name: vLLM emits its own model_name, and a collision makes Prometheus rename the scraped one to exported_model_name, which quietly breaks joins. lumen_model keeps both, and lets you see when the served name and your alias have drifted apart.
If you'd rather not touch Lumen
file_sd_configs watching ./targets/backends.json, written by a cron job that reads config.yaml and emits the same payload. Prometheus watches the file with inotify, so no reload there either. Less elegant, but zero code in the app.
Dynamic on the query side
Write everything with by (lumen_model) and it self-extends:
 
promql
Plain Text
sum by (lumen_model) (vllm:num_requests_waiting)
In Grafana, one time series panel per metric with that grouping already adds a line per new model. Use a $model template variable from label_values(up{job="backends"}, lumen_model) only if you want per-model repeated rows.
Alerts are the same idea. Label-generic rules cover new models automatically:
 
yaml
Plain Text
- alert: BackendDownexpr: up{job="backends"} == 0for: 5mannotations:summary: "{{ $labels.lumen_model }} on {{ $labels.host }} is down"
One gap worth naming: a brand new model with a broken URL shows up as a down target, which looks the same as a crashed model. If that bothers you, have the SD endpoint only emit backends Lumen has successfully health-checked at least once.
